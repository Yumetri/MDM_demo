# API 응답·오류·페이지네이션 규약

상태: 초기 규약 초안. cursor 페이지네이션과 일관된 응답·오류 재사용은 확정된 요구사항이다. 아래 필드 이름, 기본값, 코드, 메시지 언어는 구현을 위한 초기 제안이며 토론을 통해 조정한다.

## 성공 응답

단건 응답은 `data`에 결과, `meta`에 공통 메타데이터를 담는다.

```json
{
  "data": {"id": "example-id"},
  "meta": {"request_id": "example-request-id"}
}
```

목록 응답은 `data` 배열과 `meta.page`를 사용한다.

```json
{
  "data": [{"id": "example-id"}],
  "meta": {
    "request_id": "example-request-id",
    "page": {
      "next_cursor": "opaque-token",
      "has_next": true
    }
  }
}
```

- 마지막 페이지는 `next_cursor: null`, `has_next: false`이다.
- 빈 목록은 `data: []`로 응답한다.
- HTTP 상태는 실제 처리 결과를 표현한다. 생성은 201, 본문 없는 성공은 204를 사용할 수 있다. 204에는 응답 envelope를 넣지 않는다.
- 클라이언트는 성공·실패를 메시지 문자열로 판별하지 않는다.

## Cursor 페이지네이션

- 입력은 선택적 `cursor`와 `limit`이다. 초기 기본안은 `limit=20`, 허용 범위는 1~100이다. 범위를 벗어나면 검증 오류를 반환한다.
- 초기 방식은 다음 페이지로 진행하는 단방향 페이지네이션이다.
- OFFSET을 cursor처럼 포장하지 않고 정렬 키를 기준으로 다음 구간을 조회한다.
- 정렬은 유일한 순서를 보장해야 한다. 업무 정렬 키가 중복될 수 있으면 고유 식별자를 마지막 정렬 키로 포함한다.
- cursor에는 정렬 경계값과 버전을 담는다. 필터·정렬 등 조회 조건이 달라진 cursor는 거부한다.
- cursor는 서버가 검증하는 불투명 토큰이며 클라이언트가 해석하거나 구성하는 계약을 제공하지 않는다. 구체적인 인코딩·변조 검증 방식은 구현 시 확정한다.
- cursor를 권한 증명으로 사용하지 않는다. 매 요청마다 현재 사용자의 접근 범위와 필터를 적용한다.
- `limit + 1`개를 조회해 다음 페이지 유무를 판별한다. 반환한 마지막 항목의 정렬 키로 `next_cursor`를 만든다.
- 잘못된 형식, 지원하지 않는 버전, 조회 조건 불일치는 `INVALID_CURSOR`로 통일한다.
- 변경 중인 데이터에 대해 스냅샷 일관성을 보장한다고 약속하지 않는다. 정렬 키 변경·삽입·삭제가 페이지 순회에 미치는 영향은 해당 API에 문서화한다.
- 총 개수는 기본 응답에 포함하지 않는다. 필요성이 확인되면 별도 계약으로 추가한다.

## 오류 응답

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "요청 값이 올바르지 않습니다.",
    "details": [
      {
        "field": "query.limit",
        "code": "OUT_OF_RANGE",
        "message": "1 이상 100 이하의 값을 입력해 주세요."
      }
    ]
  },
  "meta": {"request_id": "example-request-id"}
}
```

- `code`는 클라이언트 분기에 사용하는 안정적인 식별자다. 같은 코드의 의미를 임의로 변경하지 않는다.
- `message`는 카탈로그의 일관된 기본 문구를 사용한다. 초기 문구는 한국어이며 최종 언어·다국어 정책은 미정이다.
- `details`는 구조화된 항목의 배열이고 추가 정보가 없으면 `[]`로 반환한다. 필드가 없는 오류의 `field`는 `null`이다.
- `request_id`는 성공·오류 응답과 서버 로그에서 동일한 요청을 추적하는 값이다.
- SQL, 스택 트레이스, 내부 예외 문자열, 비밀정보와 민감한 원본 입력을 응답에 노출하지 않는다.

## 공통 오류 카탈로그 초안

| 코드 | HTTP 상태 | 기본 메시지 | 발생 조건 |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | 422 | 요청 값이 올바르지 않습니다. | 요청 파싱·스키마·필드 제약 검증 실패 |
| `INVALID_CURSOR` | 400 | 페이지 커서가 올바르지 않습니다. | cursor 해석·버전·조회 조건 검증 실패 |
| `UNAUTHENTICATED` | 401 | 인증이 필요합니다. | 인증 누락 또는 실패 |
| `FORBIDDEN` | 403 | 이 작업을 수행할 권한이 없습니다. | 인증된 사용자의 권한 부족 |
| `NOT_FOUND` | 404 | 요청한 대상을 찾을 수 없습니다. | 대상 또는 경로가 존재하지 않음 |
| `METHOD_NOT_ALLOWED` | 405 | 지원하지 않는 요청 방식입니다. | 해당 경로에서 허용하지 않는 HTTP 메서드 |
| `CONFLICT` | 409 | 현재 상태에서는 요청을 처리할 수 없습니다. | 중복 또는 현재 상태와 충돌 |
| `INTERNAL_ERROR` | 500 | 요청 처리 중 오류가 발생했습니다. | 예상하지 못한 서버 오류 |

도메인 오류는 업무 의미가 드러나는 구체적인 코드로 추가한다. 예상하지 못한 모든 DB 오류를 중복 오류로 간주하지 않는다. 식별 가능한 제약조건 위반만 해당 업무 오류로 변환한다.

## Dimension 코드 자동 생성 실패 안내

[Dimension](features/dimension/README.md)의 코드 자동 생성 실패에 공통으로 사용하는 합의된 메시지다. 현재 미구현이며 오류 코드·HTTP 상태와 응답 매핑은 아직 정하지 않았다. 차원별 코드 자동 생성 조건은 각 기능 문서에서 관리한다.

| 발생 조건 | 합의한 메시지 |
| --- | --- |
| 자동 생성한 코드가 이미 존재함 | 자동 생성된 코드가 이미 존재합니다. 코드를 직접 입력해 주세요. |
| 해당 Dimension의 코드 자동 생성 조건을 충족하지 못함 | {dimension}에서 코드를 자동으로 생성할 수 없습니다. 코드를 직접 입력해 주세요. |

`{dimension}`은 코드 자동 생성에 실패한 차원의 이름(예: `company`)으로 치환한다.

## 재사용과 변경 절차

- 공통 성공·목록·오류 DTO를 정의하고 각 엔드포인트의 구체적인 스키마를 OpenAPI에 노출한다.
- 프레임워크의 요청 검증 오류, HTTP 오류, 알려진 애플리케이션 오류, 예상하지 못한 오류를 공통 예외 처리기로 변환한다.
- 오류 변환 시 인증 안내 등 HTTP 의미에 필요한 헤더를 유지한다.
- 코드·기본 메시지·HTTP 상태는 중앙 카탈로그에서 관리한다. 라우터에 같은 정의를 복제하지 않는다.
- 새 API·오류·페이지네이션 동작을 구현할 때 이 문서, 카탈로그, OpenAPI, 계약 테스트를 함께 갱신한다.
- 공개된 필드나 오류 코드의 의미를 변경할 때는 호환성 영향과 전환 방법을 기록한다.
- 아직 구현하지 않은 규약은 구현 완료로 표시하지 않는다.
